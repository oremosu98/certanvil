# Lift B1 (Progress, Analytics, Daily Review) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** At phone width, Progress, Analytics and Daily Review look and flow exactly like the founder-approved E2E screens, wired to real data.

**Architecture:** Progress and Analytics get phone-only screens rendered into `#ios-progress` / `#ios-analytics` by two new feature files. Each file has a pure model and a pure HTML function (UAT-testable in a vm sandbox through `_fnBody`) plus a mount function. The desktop renderers call the mount at their end, the same way `home.js` calls `renderIosHome()`. Daily Review keeps its markup. It is restyled in `lift-ios.css`, with a few small hooks added in `features/sr-review.js`. No new data layer: everything reads the functions the desktop pages already use.

**Tech Stack:** Vanilla JS IIFEs exporting to `window`, CSS scoped under the `(max-width: 899px)` gate, UAT (`tests/uat/*.js`, vm sandbox), Playwright.

**Spec:** `docs/superpowers/specs/2026-10-21-ios-lift-b1-design.md`. The E2E is the design source of truth: branch `feat/cert-ios-e2e` (worktree `.claude/worktrees/june-e2e`), files `mockups/cert-ios-progress.html`, `mockups/cert-ios-analytics.html` (commit `b31c7df6`) and `mockups/cert-ios-review.html`.

## Global Constraints

- **Fidelity rule:** same layout, copy, spacing, type, colour and motion as the E2E screen. Any deviation is shown to the founder and approved before it ships.
- Phone only: `(max-width: 899px)`. Desktop renders exactly as today.
- `app.js` is at its ratchet (8301 lines). Add no lines to it.
- CSS is ported from the mockups with `scratchpad/port_css.py <css> <scope> <prefix>`, using the prefixes `ip-` (progress), `in-` (analytics) and `iv-` (review). The ported CSS goes in new sections of `lift-ios.css`.
- Motion uses BRAND.md §6 tokens:
  - `--ease cubic-bezier(0.16,1,0.3,1)`
  - press 150–160ms
  - underline move 220ms
  - bar/ring sweep 800–1100ms
  - 60ms stagger
  - Map sheet: 360ms in, 200ms out
  - Reduced motion collapses all motion to fades.
- Touch targets are at least 44pt. A 40px CSS target is 44pt on the device at the app-wide `html{zoom:1.10}`.
- No em-dashes in on-screen copy. Theme tokens only, no hardcoded hex.
- Gated lane files (`sw.js`, `auth-state.js`, `cloud-store.js`, `lib/supabase.js`) are not touched.
- Side-by-sides are compared at 402pt, not 390.
- Cross-platform: verify on Desktop (unchanged), Safari/WebKit (Playwright webkit project), mobile web at 390/402, and the iOS Capacitor app in the Simulator.
- Branch: `feat/lift-b1` in the main checkout. It ships as one release, v8.185.0.

## Review Focus

1. **A brand-new user with no history.**
   - Progress shows every topic as untouched with 0% covered, and there is no "Drill this next" card.
   - Analytics shows the E2E-style empty state in place of six empty pages.
   - The Map shows every tile untouched and hides the "Your 3 weakest topics" box.
   - Owned by Tasks 3, 5 and 6.
2. **A cert other than Network+.**
   - Sec+ has a different domain count, and AI-901 has very few topics.
   - Progress pills and Map rows come from the active cert's own domains. The pager has as many pages as pills.
   - Owned by Tasks 3 and 5.
3. **Fewer than three weak topics.** The action line lists only the topics that exist ("Your weakest topic", "Your 2 weakest topics"). When nothing is weak or developing, the box is hidden. Owned by Task 5.
4. **A topic name containing `&` or `<`.** Labels, `aria-label`s and `data-` attributes are escaped. A tile tap still drills the right topic. Owned by Tasks 4 and 6.
5. **Rotating the phone or resizing past 899px while a phone screen is open.** The desktop page shows correctly, and nothing is stuck hidden. Owned by Task 2.

### Task 3: Progress model

**Files:**
- Modify: `features/ios-progress.js`
- Test: `tests/uat/491-ios-progress-model.js`

**Interfaces:**
- Consumes: the row shape from `_buildProgressRows()` in `features/progress.js`: `{t, label, pct|null, total, attempts, daysSince|null, lastDate, domainKey, obj, trend}`. Also the cert's domains as `[{key, name, examPct}]`; read them the way `_renderProgressSummary` does.
- Produces: `_iosProgressModel(rows, domains, state) -> model`, where `state = {filter:'all'|'weak'|'untouched'|'strong', sort:'worst'|'best'}`:
  - `model.next`: `{t, label, pct}` for the weakest studied topic, or `null`.
  - `model.stand`: `{coveredPct, avgMastery, seen, total, weak, untouched, strong}`.
  - `model.pages`: `[{key:'overview', label:'Overview'}, ...one per domain {key, label, name, examPct, mastery, studied, total, untouched, rows}, {key:'insights', label:'Insights'}]`.
  - `model.insights`: `{weakest, strong, untouched, untouchedCount, recent}`, each a list of `{t, label, pct}`.
  - `model.filter` and `model.sort` echo the state.

- [ ] **Step 1: Write the failing UAT.**

  - Assertions:
    - `next.t` is the 30% topic.

    - `pages.length === 4`.
    - Filter `'weak'` leaves only rows under 55% in each domain page.
    - Sort `'best'` reverses the order.
    - An empty-history fixture (all pct null) gives `next === null` and `coveredPct === 0`.
  - The thresholds are the ones `progress.js` already uses for its filters. Read them and name them in the test.

- [ ] **Step 3:** Implement `_iosProgressModel`. It must be pure (no DOM, no globals) so `_fnBody` can run it in the vm sandbox. Export it on `window`.
